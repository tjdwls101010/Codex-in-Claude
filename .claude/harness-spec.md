# Harness Spec — Codex-in-Claude

## Context

This repository *is* the harness component it ships: a Claude Code plugin (`codex`) containing a single skill (`codex`) that lets Claude drive the OpenAI Codex CLI as a managed subagent. There is no application code to support — the skill and its Python CLI are the entire product.

- Language / runtime: Python 3.10+, standard library only (no `jq`, no third-party packages).
- External dependency: `codex-cli` (verified against **0.144.1**), authenticated via `CODEX_HOME`.
- Host: Claude Code 2.1.220.
- Distribution: Claude Code plugin, self-marketplace in this repo; dev install via symlink into `~/.claude/skills/codex`.
- Documentation language: **English** for SKILL.md and `references/`; Korean README; Korean trigger keywords inside the skill `description`.
- User proficiency: high. Comfortable with hooks, plugins, skills, and CLI internals; already ships a plugin (`skills-for-repo-wiki`) using this exact packaging pattern. Interview was conducted in Korean at full technical vocabulary.

Full design reasoning, measurements, and implementation order: `docs/plan/codex-skill-implementation-plan.md`.

## Goals

In the user's own words: *"코덱스를 클로드코드의 자체 integrated된 서브에이전트처럼 활용할 수 있는 스킬을 만들고 싶은거지."*

Concretely, Claude should be able to:

1. Hand work to Codex and get a run handle back immediately.
2. Continue an earlier Codex thread rather than starting cold every time.
3. Watch a Codex run's log live and intervene when it goes wrong.
4. Leave Codex running while Claude does something else.

Two constraints the user stated explicitly, and which shape every component below:

- **No use-case rails.** *"그 사용목적을 일일이 스킬에 명시할 필요는 없을거 같아. 이건 일종의 레일이니까."* The skill teaches mechanism, gotchas, and judgment criteria — never a menu of approved tasks.
- **Context discipline is a first-class requirement.** *"코덱스가 접근한 파일의 내용을 전부 클로드에게 그대로 돌려주면 컨텍스트가 낭비될 거 같거든. 이건 일종의 트레이드오프겠지. 이 부분에 대해선 실측을 하며 최적의 전략을 세울 필요가 있을거 같아."* Filter defaults are to be chosen by measurement, not assumption.

### Refinements forced by measurement (R10–R28)

Same form as R1–R9: each one is a place the plan said something that turned out to be wrong, found by running the thing rather than by reading it.

- **R10 — `batch clean`'s protection cannot be derived from the group graph.** Plan §3.6 plus §1.4 listed the refusals as live members, dirty worktrees, and a derived group. `derived_from` is one hop deep and evaporates the moment an intermediate group is cleaned: with p1 → p2 → p3, a `batch clean --group p2 --force` leaves p1 looking unreferenced while p3 is still running inside p1's worktree — reproduced, and it deleted from disk the exact directory a live run had as its cwd. The right question is not lineage but occupancy: **is any non-terminal run's recorded cwd inside this worktree.** A run's own cwd cannot go stale the way a graph edge can. The `derived_from` check stays, because it gives the better message while the chain is intact.

- **R11 — "keyed by run, not by worktree" (§3.4, D30) was necessary and not sufficient.** The plan correctly saw that a worktree-keyed set would make every `--resume-from` member overlap its own predecessor. What it never noticed is that **Codex reports absolute paths**, so under worktree isolation three members editing the same `src/parser.py` produce three distinct strings and intersect to nothing — `overlaps` reported a clean run in precisely the situation it exists to warn about, and the cleaner the isolation the more reliably it lied. Caught by T2 I10, not by T1, because the unit fixture planted repo-relative paths, a shape real events never have. The obvious fix — relative to each run's own cwd — then introduced a false positive (two repositories each with an `output.txt`) and a false negative (two members rooted at different depths of one repository). The key is a pair: `--git-common-dir`, which every worktree of one repository shares and no two repositories do, plus the path relative to that run's own top level.

- **R12 — "recorded in place" (§3.2) was true of one line of JSON and nothing else.** A member that fails to spawn keeps its manifest slot, as planned. But every later view of a group resolves membership through run ids, and that member has none — so it existed only in `batch start`'s reply and vanished the moment that scrolled past. Measured: a group asked for two members and given one reported `group_state: completed`. Those slots are now first-class in every group view, they count toward `partial`, and `--follow`'s terminal line carries `unstarted=N`.

- **R13 — the plan never made a group discoverable.** §3.3 defines `status --group <name>`, and every group command takes a name the caller is assumed to have. A session that did not start the batch has no way to learn one: `status` listed runs and said nothing about groups. Measured in a headless e2e session, which found three runs, declared out loud that they "were individual starts, not a batch group", correctly deduced that plain `resume` cannot isolate writers, and continued three of them into one shared directory — **reasoning perfectly well from a false premise the tool had handed it**. `create_run` had been recording each run's group in meta.json since M4a with a comment saying it was there so `status` could answer this; `status` now does, and also lists the project's groups.

- **R14 — D35 recorded that resume members inherit their directory, and never drew the consequence.** `resume` has no worktree option at all, so continuing several writers at once is **unisolatable by construction**; only `batch start --resume-from` can assign one per member. Documentation was measured to be insufficient here twice over: a session that had the guidance available still used three individual `resume` calls into one directory, and escaped damage only because the three edits happened to land in three different files. The conclusion is a general one — where the tool knows a fact the caller cannot see, the tool should say it at the moment it matters rather than leaving it to prose. `concurrent_writers` on `start`/`resume`, and the same check registry-wide in `doctor`.

- **R15 — "pair `--follow` with Monitor" (§3.3) is right only when another turn is coming.** The plan's reasoning was the Bash tool's 600-second ceiling, which is correct as far as it goes. In a single-turn context the follower dies with the turn and nothing arrives. Measured: two headless sessions each started their batch correctly, launched a background wait, and ended the turn promising to report back — delivering the user a promise instead of the findings they asked for. With one turn, `status --group --follow --follow-timeout <sec>` in the **foreground** is the right shape. And separately: `batch start` returning is not the batch being done, and the group finishing is not the results being collected.

- **R17 — a flag nothing asserts on is a flag that can stop working silently.** `--include-external` had zero test coverage, and a change to a neighbouring line disabled it without anything going red. Asked afterwards how much more of the surface was in that state, the answer was measurable rather than a guess: diffing the parser's registered flags against every string in the suite found four more. None of the four turned out to be broken — but they were in the same position, and that position is the defect. All 43 user-facing flags are now named by at least one test, and that diff is worth re-running before any release.

- **R25 — a guard that only checked one direction of the same mistake.** `--since` was refused when it pointed *past* the end of the events file, on the reasoning that such a cursor "is almost always one fed back from a different run". An offset that happened to land *inside* the file was accepted — same mistake, same cause, opposite side of the boundary. The read then started mid-line, so the event straddling the offset arrived as an anonymous `_unparsed` blob with its first half missing and the cursor advanced past it: one event destroyed, exit 0, under a docstring promising "nothing duplicated, nothing skipped". A cursor always lands just after a newline because that is the only place this code leaves one, so checking the preceding byte is the whole fix.

- **R26 — the check and the fact it depends on were in different critical sections, i.e. in none.** `refuse_concurrent_turn` scanned the registry for a live turn on a thread; the caller then built the run, and the new run only became visible to the *next* scan when `create_run` wrote its meta.json. Between those two points the answer was true and unpublished. Two `resume` invocations a fraction of a second apart both saw an idle thread, both reported success, and two Codex processes appended to one rollout file — the exact F4 corruption the guard exists to refuse. The window was not small either: the scan reads every run's meta.json before it can answer, so it widened with the registry. The guard now lives inside `create_run` under a per-thread lock spanning check-to-publish, released before the worktree is cut so a foreground turn cannot hold it for minutes. Reverting the lock fails the regression test six times out of six.

- **R27 — a name is not an identity.** `batch clean` releases a group name when nothing is left behind, and a manifest that has been claimed but has no members yet looks exactly like an abandoned one. So a clean could release a name a `batch start` was still spawning into, a third process could claim it, and the first batch's `write_members` — an unlocked read-modify-write — would merge its members into the stranger's manifest: one file with C's `requested` and A's members, which is R12's "asked for three, given two" lie wearing a different hat. `claim_group` now stamps each claim with an epoch and `write_members` refuses a manifest that is no longer its own, naming what it had already spawned so those runs stay reachable.

- **R28 — the same question, asked twice, drifts. Again.** `concurrent_writers`, at run creation, has always treated `/p` and `/p/sub` as one tree via `is_within` in both directions. `doctor` — the report a caller consults *afterwards*, precisely when they suspect something is stuck — grouped live runs by exact `cwd` string, so those two runs landed in two buckets of one and it warned about neither. The creation-time check had already seen what the after-the-fact report could not. This is R20's lesson arriving a second time in one session, which is the reason to state it as a rule rather than a fix: **two implementations of one question is a defect already, before either of them is wrong.**

- **R24 — the invariant had a documented flag pointing straight through it.** `--config` hands a raw `-c key=value` to Codex, and `codex`'s `-c` is last-value-wins for a repeated key. The wrapper emitted its own enforced `-c sandbox_mode=` *before* the caller's raw entries, so `--config 'sandbox_mode="danger-full-access"'` simply won. Measured against the real binary, same prompt both ways: with the raw entry last the write to `/tmp` returned exit 0 and the file appeared; with the enforced entry last it returned `Operation not permitted`. Throughout, `meta["sandbox"]` and therefore `status` reported `read-only` — and since `extra_config` is inherited by every resume that does not pass `--config` itself, the drift rode along for the rest of the thread. This is B3, the one behaviour the skill exists for, defeated by a flag in its own `--help`. Two guards now, deliberately redundant: the four keys the wrapper sets are refused outright with the flag that owns each one named, and the argv order is inverted so a key nobody thought to reserve still cannot outrank an invariant. The general lesson is narrower than "validate input": **a pass-through option is a second, unaudited way to set everything the tool sets itself**, and it needs listing against the settings the tool considers its own.

- **R22 — two fixes that were each right and together were a regression.** Publishing a run's `meta.json` before cutting its worktree (R18) made it visible to `reap`, whose grace period for a supervisor-less `starting` run is thirty seconds of file mtime. `git worktree add` is allowed sixty. So a large checkout on a slow disk leaves a *live* run looking half a minute dead, `orphaned` is terminal, and the run therefore drops out of `batch clean`'s live-member guard and out of the occupancy check protecting its worktree — at which point `-f -f`, added by the same commit precisely to defeat git's `initializing` lock on a worktree whose owner died, removes a checkout whose owner is alive and still writing into it. The two changes cancelled each other. A run now records `creator_pid` before it does anything slow, so `reap` asks a process rather than a clock. The transferable part: a heuristic's safety is a property of *when* the thing it reads is written, and moving that write is a change to the heuristic even when the heuristic is not touched.

- **R23 — unknown is not terminal.** `batch clean`'s live-member loop skipped a member whose `meta.json` would not parse, while the removal loop below it still found that member's worktree by the `<run_dir>/wt` convention. A run last recorded `running` therefore lost the only copy of its work with no `--force` ever passed. The skip read as "nothing to check here"; what it actually meant was "I cannot tell whether this is running", which is the case for refusing, not for proceeding. Also from the same shape: `vanished_members` said "its run directory is no longer in the registry" about a directory that was still there with a corrupt meta — sending the caller away from work still on disk, while the same payload's `unreadable` field said the opposite.

- **R18 — the fix a commit claimed, and the test that let it claim it.** A batch killed while spawning left a checkout belonging to no member of any group. Writing the manifest slot *before* the spawn looked like the fix, its regression test went green, and the commit said so. The test passed six times in ten; the four failures were the defect, still there. The slot cannot carry a run id — the id is minted inside `create_run` — so the guard was in the wrong place entirely. Closing it took four changes plus a fifth underneath them all: **`--force` did not force.** `git worktree add` holds a lock reading `initializing`, a batch killed inside the add leaves it locked forever, and `git worktree remove --force` refuses a locked tree; it wants `-f -f`. `batch clean` had been printing that it "lifted every protection at once" while a checkout survived it. Two process notes: a test that passes intermittently is a finding, not noise, and "did the fix do what the commit says" needs asking by something other than the author.

- **R19 — a silently ignored flag is a false premise the caller then reasons correctly from.** `status --run <id> --follow` returned one snapshot and exited: `--follow` is registered on `status` as a whole but only the `--group` branch reads it. Guarding that symptom left the precedence underneath it untouched, so `--run X --group g --follow` walked past the new guard and the `--run` branch won again — found by a Codex `review` member pointed at the commit that added the guard. Both are R13's shape: the tool hands back an answer the caller reads as "I waited for this."

- **R20 — one rule enforced at the top level and not one level down.** `load_tasks` refuses unknown *top-level* task fields, with a comment saying exactly why: "the failure mode of a silently ignored field is a run that quietly used the group default instead". `review` is the only nested object a task has, and inside it the rule did not apply — `title` was dropped without a word, and combinations the Codex CLI rejects were passed straight through to fail asynchronously. Both callers now build the flags in one place. Worth generalising: a validation principle stated in a comment tends to hold exactly at the depth someone was looking at when they wrote it.

- **R21 — `${CLAUDE_PLUGIN_ROOT}` is expanded in a permission rule and `$HOME` is not.** R6 measured the first and it was reasonable to assume the second followed. It does not, so the `settings.json` rule this project has been documenting for symlink installs never matched anything, and every bridge call under it was refused. `Skill(codex)` also needs its own rule or the skill cannot load at all, and the `Bash(...)` rule is never reached. And the plan's guess that a long `batch start` would break the text match was right about the symptom and wrong about the cause: length is irrelevant against a prefix and a trailing `*`; the **line continuation** a model reaches for because the command is long is what breaks it.

- **R16 — a specified, assigned item was never implemented, and nothing at the milestone level noticed.** §1.7's `doctor` warning for non-terminal runs sharing a cwd was written into the plan, assigned to M4b, and simply not built; the pre-release sweep found it. Milestone checks verified what was written against what was planned for *that* milestone, and this fell between two. Worth carrying forward as a process note: a plan item's completion should be checked against the plan, not against the diff.


### Refinements forced by measurement (R30–R53, the 2026-08-13/14 round)

This round put thirteen defect candidates through adversarial refutation *before* fixing any of them, with three already-confirmed ones planted as a control group. Only survivors were fixed. Each entry below says what was wrong, how it was found, and which test fails if the fix is reverted.

- **R30 — the suite could not notice its own absence.** Moving `tests/` to `tests/legacy/` shifted every `__file__`-rooted path constant by one directory and killed all 301 tests. The damage was not that they broke but *how*: the documented command answered `NO TESTS RAN` with exit status 0, which reads as a clean pass to anything that skims the tail, and there is no CI to disagree. Found by running the documented command and looking at the count rather than the status. `tests/260813/test_suite_integrity.py` now asserts that every discovery command written in CONTRIBUTING.md and the wiki collects a nonzero number of tests and imports cleanly, that every directory holding `test_*.py` is reachable from one of them, and that every path either suite computes from its own location still resolves. Its path check reports an expression it cannot evaluate rather than skipping it — a checker that quietly passes on what it failed to understand is the defect it is looking for.

- **R31 — `batch start --foreground` ran the batch one member at a time.** `task_args` copies the caller's whole namespace onto every member and `_batch.py` never mentions `foreground`, so `create_run` called `supervise()` synchronously and the spawn loop waited out each member's entire turn. Measured: three members hanging two seconds each took 7.15 s, with run ids two seconds apart. Nothing announced it; the reply has the same shape either way, so the only symptom was that a batch took N times longer than expected. Refused rather than made concurrent — there is already a working way to block on a batch (`status --group --follow`), and building a second supervision model for a flag nothing documents would be the larger change. `test_batch_modes.py`.

- **R32 — the worktree preamble stated a count it never read.** `uncommitted_count` returned 0 when `git status --porcelain` failed, so "there are none" and "I could not tell" left by the same door, and the number went to Codex as fact. V-18 is the record of this paragraph existing to *correct* a confident falsehood, which makes it the worst possible place to manufacture one. The precondition is not exotic: a corrupt `.git/index` makes `status` exit 128 while `rev-parse` and `worktree add` both still succeed, so the batch gets far enough to write the sentence. Returns `None` now, matching the module's own sentinel convention; the known-case sentence is unchanged to the byte. `test_worktree_honesty.py`.

- **R33 — R28 fixed the pair it was written for and left the flag beside it.** `stop --run X --all` silently ignored `--all`, answering only the first branch that matched. Which flags actually compete is per command and cannot be inferred centrally — `stop --all` is a third selector, while `status --all` only lifts a row-count cap and is meaningful next to `--run` — so each caller now states its own selector set rather than the rule guessing. The boundary is itself a test: `status --run X --all` must keep working. `test_selectors.py`.

- **R34 — the concurrent-turn guard was blind to exactly the runs it could not rule out.** `refuse_concurrent_turn` builds its live set from `iter_runs`, which drops any run whose `meta.json` will not parse. Both the thread id and the state live in that file, so such a run can be shown neither to be on another thread nor to have finished — and this guard is the only thing standing between two turns and one rollout file. This is R23 ("unknown is not terminal") at a different guard; the machinery R23 built (`meta_unreadable`, `unreadable_runs`, `note_unreadable`) was already there and unused here. The same hole existed in `pair_with_previous`'s group-wide check, where the per-member guard downstream cannot stand in for it: by the time that one fires, earlier tasks have already resumed. `test_unreadable_runs.py`, `test_unreadable_group.py`.

- **R35 — a corrupt group manifest was a dead end `--force` could not reach.** The check ran before `--force` was consulted, so the flag that exists to lift every other protection could not lift this one, and the members' worktrees — the only copy of what those runs produced — were stranded. The asymmetry is what marks it as a gap rather than a policy: `--force` already overrides a corrupt member `meta.json`. Membership does not actually depend on the manifest, since each run records its own group when its directory is claimed; what is genuinely lost is start *order*, so only `--resume-from` refuses. `test_unreadable_group.py`.

- **R36 — five commands told the caller a run had never existed while its directory sat on disk.** `find_run` returns `(run_dir, None)` for an exact-id hit whose meta will not parse, and each site tested only the meta. R23's shape again: a caller sent away from work that is still there, with nothing to say where to look. The error now names the run directory and its event stream, which is a separate file and usually intact. `test_unreadable_runs.py`.

- **R37 — a damaged event stream was summarised as a clean one.** `read_events` already preserves a line it cannot parse as an anonymous `_unparsed` blob and `log` renders it, but `scan_progress` had no branch for it, so `status` and `result` — the two surfaces read programmatically — reported nothing. Kept out of `errors`, which counts Codex reporting a problem with the work rather than the bridge failing to read what Codex said; summing them hides whichever is smaller. Reported only when non-zero. `test_unparsed_events.py`.

- **R38 — the refuters disagreed about scope, and the control group is what caught it.** Of thirteen candidates, one refuter killed a control by arguing that a corrupt `meta.json` cannot arise through the tool's own operation and therefore does not count. Four other verdicts leaned on the same rule while three leaned on its opposite, in the same round, on the same question. This repository settles it the other way — externally-caused corrupt state is explicitly in scope, and R23 is a fix for precisely it — so the bar is "does the code then misinform or destroy", not "can the tool produce the corruption". **This was a defect in how the round was briefed, not seven independent lapses of judgement**, and it is recorded here because the next round will brief refuters again. The strongest verdict in the round was the one that refuted *empirically*, by running the real CLI under four corruption conditions rather than arguing from the code.

**R39–R43 came from the adversarial round on `--as-ready` *after* it passed the twenty tests written alongside it.** That is the argument for running the round rather than trusting a green suite, and it is the third time in this project's history that a round found defects in the previous round's own work.

- **R39 — the wait-chain exemption was one link long.** `refuse_concurrent_turn` exempted exactly the direct predecessor, so registering p3 behind p2 while p1 was still running was refused, naming the *grandparent* as the live turn. Every stage of a chain is ordered by construction, so nothing could have raced; the effect was to force the caller to poll each stage until it visibly started before the next could be registered — which is the waiting the flag exists to remove. **Found twice independently**: by a lens reading the function, and by an agent driving the real CLI who simply chained a third phase and got refused. The fix walks the transitive chain, bounded, because `waits_for` is a field on disk like any other and a cycle would hang the guard rather than refuse. Exempting every `waiting` run instead would have been too wide: a waiter that is not behind *us* starts the moment its own predecessor ends, so a turn begun now could still overlap it.

- **R40 — `ACTIVE_STATES` replaced six hand-written tuples and there were seven.** `cmd_status`'s top-level summary read `("running", "stalled")`, so a `waiting` member appeared in `runs[]` with its state and in none of `running`/`done`/`failed`, while the same run through `status --group` was counted as running. One field name, two meanings, decided by which view answered. The tuple was already missing `starting` before this round — the same hole at a shorter timescale, which is why nobody had noticed it. Also found by two lenses independently. The lesson is not "we missed one" but that a constant introduced to stop a class of bug has to be introduced by *searching for the class*, not by fixing the instances someone listed.

- **R41 — a guard whose only escape was `rm -rf`.** The unreadable-run check appended every unparseable run in the project with no thread filter, and `--as-ready` may not be combined with `--force`, so one corrupt run anywhere blocked every resume in the project permanently — there is no command that removes a single run. R34 chose that conservatism deliberately, for consistency with `batch clean`; running it showed the coarse version is unusable in a way `batch clean`'s is not, because `batch clean` names its own escape and this did not. The narrowing has a real mechanism rather than a relaxation: `events.jsonl` is written by Codex and `meta.json` by this wrapper, so one being corrupt says nothing about the other, and the thread id is announced in the stream. Recovery succeeds → only that thread is blocked. Recovery fails → still refused, and the message now names the directory to remove.

- **R42 — the refusal asserted something it did not know.** "thread already has a live turn" was printed when an unreadable run was the trigger and there might be no live turn at all. The guard was refusing *because it could not tell*, which is a different sentence with a different remedy. This is the exact failure class the project exists to hunt, sitting inside a fix written to close another instance of it — worth recording precisely because the author had just spent the round thinking about this shape.

- **R43 — two collision checks invented a collision.** A `--as-ready` member inherits its predecessor's directory and sits non-terminal beside it, which is the shape every concurrency check looks for, and is the one arrangement that cannot collide: the later run does not spawn Codex until the earlier one has stopped. `doctor` reported them as uncoordinated writers who "cannot tell another agent's change from your own", about a run with no process. `concurrent_writers` had the same gap at creation time. Both now exclude pairs ordered by waiting — and the pair is fixed in both places rather than one, because R20 is the record of these two implementations of one question drifting apart before.

**R44–R49 came from a SECOND adversarial round, on the fixes R39–R43 had just made.** Three rounds in a row have now found defects in the previous round's work, which stops being a coincidence and starts being a property of the method: a fix written under time pressure is the least-reviewed code in the tree at the moment it lands.

- **R44 — a chain exemption that promised more than the wait loop kept, twice.** The exemption lets a member be created while a run ahead of it is still going, on the grounds that everything ahead finishes first. The wait loop watched only its direct predecessor, so a middle waiter whose supervisor was killed became `orphaned` — terminal — the moment the loop reaped it, and the run behind it started while its *grandparent* was still mid-turn on the same thread. Reproduced directly. The loop now walks the whole chain. **The first fix for this closed the wrong half**: an abandoned *waiter* owns no Codex process and therefore cannot corrupt anything by itself, and it took another round to find that the half which does corrupt — a predecessor whose supervisor died while its Codex kept writing — was still open (R50).

- **R45 — the round added a clock and left the field callers read on the old one.** `codex_started_at` exists because `started_at` stopped being a reliable measure of work the moment `--as-ready` shipped; `elapsed_seconds` kept measuring from `started_at`, so a member queued an hour and running a minute reported sixty-one minutes of work. `codex_elapsed_seconds` is the turn. `elapsed_seconds` keeps its own meaning — how long the run has existed is still a real question, and for a waiting member it is the *only* one with an answer.

- **R46 — a trailing line with no newline is left for the next poll, and a terminal run has no next poll.** `read_events` is right to hold a partial line back while something is still writing; for a run killed at the SIGKILL rung of `stop`'s ladder, the premise has expired and the bytes are dropped by a rule that no longer applies. Same silent drop as R37, arriving from the other side.

- **R47 — `uncommitted_clause(0)` read as a double negative around a number.** "it does not contain the 0 uncommitted file(s) that exist in theirs" is true and is a strange way to say the caller's tree has nothing this one is missing. A clean tree is the ordinary case, not the edge one.

- **R48 — two ways for a wait to end wrongly.** A stop landing between the loop's flag check and its return was swallowed, and `supervise` then ran a full un-signalled turn — worse than the already-accepted race where a turn is nearly done, because here nothing had started and the stop was entirely in time. And a cyclic `waits_for` — a field on disk like any other — made the loop wait forever on an answer that cannot arrive; the bound on the walk keeps a tick finite, and refusing is what keeps the run from hanging.

- **R49 — a task naming its own resume target did not wait, and then waited on the wrong thing.** The `named` branch never set `waits_for`, so the one shape `--as-ready` promises to order was the one it did not. The first fix stored the task's raw `resume` ref — but that field accepts a thread id or a prefix, while `waits_for` is joined as a directory name, so the supervisor reported a perfectly readable run as unreadable. Resolved through `find_run` at pairing time now, and a ref absent from the registry is refused: nothing can watch it reach a terminal state.

- **R50 — the corruption itself, found by a judge re-running the round's own reproduction.** `reap` judges liveness from `supervisor_pid` alone, and `subprocess.Popen` makes Codex a child that Unix does not cascade-kill. A supervisor lost to SIGKILL or the OOM killer therefore leaves a run recorded `orphaned` — terminal — with its `codex exec` still appending to the thread's rollout. Everything reading terminal as "safe to start" then released onto it. **`reap` was deliberately not changed**: the legacy suite pins `orphaned` to mean "nothing is left to record this run's outcome", not "nothing is running", and making it wait on a live Codex would strand a hung run as `running` forever — the stale row `reap` exists to clear. Instead `still_writing` is consulted at the two places that ask whether a *thread* is free. Terminal answers "is anyone recording this"; those two need "is anything still writing this", and the questions come apart exactly when a supervisor dies alone.

- **R51 — `--force` freed a group name whose members were still running.** `kept` is populated only from worktrees found on disk, and a `kind=resume` member never has one — which is every `--as-ready` waiter. So the same reply listed a running member and declared its name free, and once another batch took the name, `owned_run_ids`' registry fallback (which matches the bare name with no epoch) made the new owner's `batch clean` refuse citing a run it had never started. A name whose members are still running is not free.

**R52 — the method's own defect, and the most transferable thing this round produced.** Both rounds fixed defects *while the review that found them was still running*, and then did not re-review the fixes. Two of the three defects the second judge ruled ship-blocking were introduced by fixes written that way, one of them fifteen minutes before it was found. The rule that follows is not "review more" but **freeze the tree, land the fixes, then run a round against a tree nobody is editing** — a reviewer reading a moving file is reviewing something that will not exist by the time it reports.

**R53 — the same mistake, twice in one round, and the rule that follows.** R40 was `ACTIVE_STATES` replacing six hand-written state tuples when there were seven. R50 was `still_writing` added at the two sites a judge had named, when twelve places turn run state into a liveness claim. A third round, on a frozen tree, found each of the remaining ten as a separate defect: `stop --group` and `stop --all` reporting success having signalled nothing; `batch clean` deleting a live member's checkout with no `--force`, in the loop whose own comment says "a live member is still writing into the very directory being removed"; `concurrent_writers` and `doctor` going silent, when they are the only surfaces that can show a cross-thread directory collision; `--follow` printing its terminal line while events were still arriving; `result` returning two different final messages ten seconds apart, neither caveated; `codex_elapsed_seconds` frozen at whatever `ended_at` an unrelated caller's `reap` happened to stamp.

**The rule: a constant or a predicate introduced to close a class of bug has to be introduced by enumerating the class.** Fixing the instances someone listed leaves a fix that looks complete and is not, and the next round finds the rest one at a time. The enumeration here is cheap — one grep over `TERMINAL_STATES` and `ACTIVE_STATES` — and it was skipped twice because a reviewer had helpfully supplied a list.

Two sites were deliberately left, recorded so a later round does not re-raise them: `reap` itself, because the legacy suite pins `orphaned` to mean "nothing is left to record this run's outcome" and making it wait on a live Codex would strand a hung run as `running` forever; and `signal_run`'s compare-and-set, because `orphaned` is already terminal and overwriting it with `interrupted` would lose the fact that the supervisor died.

**What that round did NOT find is the part worth stating.** It traced all four routes to spawning a turn on a thread — `resume`, `batch start --resume-from`, an `--as-ready` waiter releasing, and `--force` — and found no remaining hole; two soak agents driving one repository concurrently, killing supervisors mid-chain, independently confirmed it. **The F4 rollout corruption is closed.** Everything the round found is a caller being misinformed, which is this project's other failure class and a real one, but nothing in it destroys work.

**Two findings about the tests themselves, which the round asked for deliberately.** A reviewer was pointed at `tests/260813/` and asked which tests were written to pass rather than to catch. It found the mutual-exclusion test setting up a live predecessor *and* a waiting member together, so the live predecessor alone caused the refusal and the test could not tell whether `waiting` protected anything — it passed either way. And it found the handshake test's stated rationale backwards: a chained member inherits its predecessor's thread id before the supervisor is ever spawned, so the poll was already exiting on the thread id, not on the `waiting` branch the docstring credited. Both are fixed. A third came from the suite's own harness: `_cleanup` kills every recorded `supervisor_pid`, and a test that calls a supervisor function in-process records its own caller there — the whole suite exited 137 with no output.

**What was refuted, and why it is worth keeping.** Seven of thirteen candidates did not survive, and knowing what was suspected saves the next round a lens: `codex --version`'s exit code is unchecked but the flag is parsed before config and auth and returned cleanly under four corruption conditions, and the value is cosmetic; a broken `started_at` degrades to `null` rather than to a wrong number, from a single write site fed by a branch-free function; `worktree_prune`'s return value cannot resurface as a later "already registered" because `prune` has exactly one caller and that string is never emitted; `registered()` and `query_threads()` returning `[]` on failure is real but designed-for and pinned by a test that asserts the degraded contract — recorded as an accepted tradeoff rather than an absence, so it is not re-found; `supervisor.log` is load-bearing rather than ballast, being the only place an uncaught exception in the supervisor's own Python can land and the redirect that keeps a detached child off a closed pipe; and `batch start --force`'s second effect is one rule with two enforcement sites, documented in `references/orchestration.md`.

### What is still unmeasured after the 2026-08-04 round

The eleven open items from `docs/plan/260802/README.md` were worked through on 2026-08-03; what that found is in the results section below. What is left:

- **N above 24.** Measured at 12, 16 and 24 with zero contention, every thread id distinct, and `batch start` returning in about 0.29 s per member — so `--stagger` stays out and D34's condition has still never fired, now at three times the ceiling that justified leaving it out (`docs/measurements/batch-cost.md`). What that does *not* say anything about is many simultaneous **heavy** members: a trivial prompt's turn is dominated by round-trip latency, not by anything that queues.
- **Batch collection at bigger messages.** `GROUP_MESSAGE_CAP = 4000` never engaged across N=3/5/8 — every member's final message came in between 258 and 661 bytes — so the number still has no evidence behind it, only headroom. It would take a workload whose members write long final messages to choose 4,000 rather than inherit it.
- **The plugin install's permission path.** Everything below was measured on the **symlink** install with a `settings.json` rule. `${CLAUDE_PLUGIN_ROOT}` expansion in the frontmatter pattern was last measured at v0.1.0 (R6) and is the path most users are on.
- **A group name is burned by a batch whose members all fail to spawn.** `claim_group` runs before the loop and a per-member failure does not unwind it, so a tasks file that fails *validation* costs nothing while one whose members fail *to spawn* costs the name. `batch clean --group` releases it and the name is reusable — the friction is one command deep, and the refusal now says so.
- **`status --include-external` at the fifty-thread limit.** Titles are capped now; the rest is about 830 bytes per thread, mostly `sandbox_policy` and `rollout_path`, which would be roughly 40 KB at the limit — the larger half of the cost, and the part not yet addressed.
- **Two processes on one project — measured on 2026-08-13/14, no longer open.** This item asked for a soak, on the grounds that it was where the residual risk was concentrated and needed a method that round did not use. Two were run, and they answer different questions:

  *A scripted soak* (`tests/260813/test_soak.py`) drives six worker threads through a seeded plan of real bridge subprocesses against one registry, with a reader polling `meta.json` throughout, and asserts ten invariants over the recorded history: registry preservation, no torn writes, terminal reach, thread-id uniqueness, one turn per thread, group-name exclusivity, membership agreement between `status --group` and `result --group`, one line of parseable JSON per invocation, worktree reclamation after `batch clean`, and cursor-walk exactness. It is deterministic enough to keep in the suite and was verified to be able to fail.

  *A workflow soak* ran four independent agents driving the bridge in one repository at the same time, which is the literal shape this item described — separate sessions, no shared plan, deliberately going for collisions. It produced 68 runs.

  What the two do **not** cover: a long-running soak (both are minutes, not hours), more than a handful of concurrent writers, and any real Codex process — both use the fake shim, so what is proven is the bridge's own concurrency, not Codex's behaviour under it.
- **`--grace` elapsing.** The flag is measured as accepted and honoured as a bound; the SIGINT → SIGTERM → SIGKILL ladder it bounds is covered only by T1's shim, because a well-behaved Codex exits on the first signal and cannot be made to demonstrate the rest.
- **The model a run actually uses when none is named.** `_codex.py` sets no default and isolation is on by default, so an unspecified run takes Codex's built-in default rather than the user's configured model. Measured to be the same model here, so nothing showed — which is why it is listed rather than closed.

**Linux is out of scope**, by the user's decision on 2026-08-03: this skill targets macOS. The previous wording here ("everything was measured on one macOS machine") invited someone to go and measure Linux; it is not a gap, it is the supported surface.

### Is it fit to use? — the question the round count does not answer

Four adversarial rounds ran on 2026-08-03/04 and **none came back at zero**, so the standing bar — two consecutive rounds at zero high/medium — is not met and should never be reported as met. Nineteen defects were found and fixed across those rounds, each covered by a test that fails when its fix is reverted.

That number, on its own, says nothing useful about whether the skill works. A sufficiently new lens finds something in any codebase; counting findings is a stopping rule that never stops. What the findings were is the part that carries information, and sorted by **reachability** they fall into two very unequal piles:

**Reachable in ordinary single-session use — three.** `status --run --follow` accepting the flag and ignoring it; `review --title` silently dropped from a batch member; `status --include-external` returning every thread's full prompt. All three were hit by simply *using* the skill during T5, within the first few commands of the mode that exercises them. None corrupted anything; all three misinformed.

**Reachable only under conditions someone has to create — sixteen.** A process `SIGKILL`ed inside a specific window; a `meta.json` corrupted by hand; two invocations racing on one project; a `--config` key deliberately chosen to collide with an enforced one; a group name released and re-claimed mid-spawn. Real, reproduced, and fixed — but not what a caller meets on an ordinary Tuesday.

**What ordinary use actually produced.** Roughly twenty real delegations went through the skill during this round — single runs, a four-member heterogeneous `--tasks-file` batch, a two-phase `--resume-from`, reviews against `--base` and `--commit`, an outside thread picked up by id, a supervised refactor landed after one correction, and 52 concurrent runs at N=12/16/24. Every batch was collected, every worktree accounted for, every `overlaps` warning correct, and nothing was silently wrong. That is the evidence for fitness, and it is a different kind of evidence from the round count.

**Where the residual risk actually sits: two processes on one project at once.** Most of what rounds three and four found lived there, and that class is the hardest to prove closed. A single session driving the skill sequentially does not reach it. Two Claude sessions on one repository, or an autonomous loop, do.

**A better stopping rule, offered because the original one may not be reachable.** Not "two rounds at zero", but **two consecutive rounds finding nothing reachable in ordinary single-session use**. That is checkable, and it tracks the thing a user cares about. Keep running rounds after that — they will keep finding things, further out and smaller, and that is the review working rather than the skill failing.

**The 2026-08-13/14 round, counted the same way.** Twenty-two refinements (R30–R51), of which **six were reachable in ordinary single-session use**: the documented test command reporting success while running nothing; `batch start --foreground` serializing a batch with no indication; `stop --run X --all` dropping `--all`; `--as-ready` refusing any chain longer than one hop; plain `status` counting a `waiting` member in no summary bucket; and `doctor` reporting a waiter and its predecessor as colliding writers. That takes the running total of ordinary-use findings from three to nine.

The rest needed a condition someone has to create — a corrupt `meta.json`, a corrupt manifest, a corrupt `.git/index`, a killed supervisor. **One of those is worth separating from the others**: R50 requires a supervisor to die, which is condition-created, and its consequence is the rollout corruption the entire guard system exists to prevent. `reap` and the `orphaned` state exist *because* supervisors die. Treating "you have to kill something" as the same class as "you have to hand-edit JSON" would be the wrong lesson.

**And the round did not end clean.** Its second judge ruled the tree not fit to ship, naming three defects — one of them that corruption, one introduced by a fix written fifteen minutes earlier. Those are fixed, but the round cannot count itself as the first of the two clean rounds the stopping rule needs, and the counter stays at zero. What R52 records is why: reviewing a tree that is being edited produces reports about code that no longer exists.

The signal still worth carrying: **defect discovery has never converged to zero.** Seven deliberate `overlaps` property tests found nothing, and then nine deliberate fault injections found three. Fixing those drew a round that found the fix had not worked and its own regression test passed six times in ten. Walking the option surface found four more. Opening three untouched modules found four more after that. Every one was reachable only by running the thing — never by reading it.


### T5 — the option surface against the real CLI (2026-08-03/04)

A new tier, and the reason it exists is R17's limit. R17 established that all 43 user-facing flags are **named by at least one test**. That is a real property and it is not the one that matters: `overlaps` was named by a test throughout the whole period it was blind, because the fixture planted a shape real events never have. So the flags were walked one at a time against `codex-cli 0.146.0`, with the evidence for each being its recorded `argv`, an event stream, or an observed state transition — never the absence of an error.

Coverage before this round was about ten flags with real-CLI evidence (T2's I1–I15). Everything else had unit-test evidence only.

**Mode A — one thread, start to finish.** `--label`, `--sandbox`, `--model`, `--effort`, `--priority`, `--config`, `--add-dir`, `--prompt-file`, `--no-preamble`, `--foreground`, `resume --last`, `log --since/--level/--follow/--interval/--follow-timeout`, `show --item/--max-bytes`, `status --run/--thread/--all/--include-external`. The filter levels reproduced T3's shape on a real batch workload: `compact` and `normal` byte-identical at 641 B because every command exited 0, `full` 9,633 B, `raw` 44,026 B. Resuming re-asserted sandbox, model, effort, `service_tier` and `--ignore-user-config` from the registry — I4 had only ever covered the sandbox.

**Mode B — a group.** A four-member `--tasks-file` batch with a different `kind`, `label`, `sandbox`, `effort` and `model` per member. D35's per-member worktree assignment held against real git: the two `workspace-write` writers each got a checkout, the `read-only` member and the `review` member stayed in the caller's tree. Spawning four members took 1.45 s. `overlaps` correctly reported one collision when two writers in separate worktrees both edited `tests/test_worktree.py` — R11's fix, measured for the first time through the `--tasks-file` path.

**Mode C — two phases.** `--resume-from` paired positionally, each member continued its own thread in its predecessor's worktree and cut no second checkout. Refusals measured: resuming a group with live members, a task-count mismatch (before the name is claimed, so it costs nothing), and cleaning a group another group resumed into.

**Mode D — `review`.** `--base`, `--commit`, `--cwd`. `--title` was silently dropped and is the subject of R20.

**Mode E — a thread this skill never started.** A thread created by running `codex exec` directly was found through `status --include-external`, picked up by id with an explicit `--sandbox`, and continued — it quoted its own previous reply. The next turn, given no flags at all, re-asserted that sandbox and effort from the registry. This is the first measurement of SKILL.md's claim that an outside thread is protected from the pickup onward.

**Mode F — near-misses, headless.** Two, both passing with the absence shown rather than asserted: "review these three files at once" (no `Skill` event, no `SKILL.md` read, no bridge call, and all three seeded bugs found by Claude itself), and a harder one not previously tried — "does this project document which GPT models it works with, and is that accurate" — where `GPT` appears as the subject of a documentation question rather than as an instruction to delegate. It did not trigger, and it answered the question by checking each documented claim against the code.

**Coverage, counted rather than asserted.** The bridge exposes **41 user-facing flags** across eleven subcommands (`--runs-dir`, `--project` and `-h` excluded — they exist for tests and scripting). ## Component specs

### `.claude/skills/codex/scripts/codex_bridge.py`

Single Python 3.10+ stdlib CLI. Subcommands: `start`, `resume`, `review`, `batch start`, `batch clean`, `status`, `log`, `show`, `stop`, `result`, `models`, `doctor`. All emit one line of JSON except `log`, and `status --group --follow`, which are line streams.

The entrypoint holds the CLI surface and one handler per subcommand; the machinery is in siblings — `_util`, `_registry`, `_events`, `_codex`, `_worktree`, `_run` (building a run and describing one), `_batch` (the group manifest, the batch subcommands, and the group views `status` and `result` grow for one). `_run` sits below `_batch` in the import order, which is what lets the batch subsystem live in one file without importing the entrypoint back.

Two invariants that unify the implementation, both forced by §3.8 of the plan (flag availability differs per subcommand):

- Sandbox is **always** expressed as `-c sandbox_mode="<mode>"`, never `-s`. `-s` does not exist on `resume` or `review`.
- Working directory is **always** set on the child process, never via `-C`. `-C` does not exist on `resume` or `review`.

Defaults: background, `workspace-write`, isolated (`--ignore-user-config`), `service_tier=priority` re-injected, no model pinned, no reasoning effort pinned, no hard timeout — model and effort stay unpinned but are now checked against the model catalog (`codex debug models`, exposed as `models`) before a run is claimed on disk, whenever that catalog can be read.

### `.claude/skills/codex/SKILL.md`

`name: codex`. `description` is the sole trigger signal — written to lean toward firing, naming intent rather than keywords alone, carrying Korean triggers (`코덱스`, `GPT에게 시켜`, …) and explicit near-misses (not Claude's own subagents/Task tool; not Codex Cloud or Codex-as-MCP-server). `allowed-tools` pre-approves the bridge script.

Body holds only what every invocation needs: path resolution, the CLI surface, the core loop (start → poll → judge → stop+resume → result), the context-discipline principle with its reason, the gotchas, background/parallel patterns, structured output, and cost/judgment inputs. No use-case list, no delegation methodology.

### `.claude/skills/codex/references/`

Split by the branch the model takes, not by volume:

- `environment.md` — `CODEX_HOME` resolution, isolation vs inherit with measured numbers, auth, sandbox semantics and the escalation story, `service_tier`, reading `doctor` output.
- `event-stream.md` — both event schemas (stdout API and rollout file), filter levels with the measured calibration table, cursor/polling, Monitor pairing, `show`.
- `orchestration.md` — running several runs as one group: the batch commands, worktree assignment and its traps, `--resume-from` pairing, how cost multiplies. Mechanism and gotchas only (D31): no catalogue of phase patterns, because the shape of a delegation varies every time and freezing it is a flexibility tax (D02, D12).
- `troubleshooting.md` — symptom → cause → fix, plus the out-of-scope list.

Launch/watch/interrupt/resume/collect deliberately stay in SKILL.md: a single invocation needs them together, so splitting them would add a routing decision with no payoff.

## Design rationale

**Why a run registry exists at all.** `codex exec resume` has no `-s/--sandbox` flag, so it falls back to `config.toml`'s `sandbox_mode`. Measured on this machine: a thread created `read-only` was resumed at `danger-full-access` and wrote a file its original policy forbade. The only way to hold a sandbox across turns is to remember the mode and re-assert it, which requires durable per-run state. Everything else the registry does (parallel-safe stop, stall detection, session-scoped cleanup) is a bonus on top of that one non-negotiable.

**Why isolation is the default.** Measured: an inherited-config run spent 46,238 input tokens on a one-line task and leaked 24 config-error events plus an unrelated plugin advertisement into the agent's own message; the isolated equivalent spent 15,863 with a clean four-line stream. Rejected alternative: always inherit (fidelity to the user's MCP/plugin setup, but ~3× the input cost on every call). Rejected alternative: a dedicated `CODEX_HOME` profile (cleanest isolation, but it severs continuity with threads created in the Codex TUI, which B2 requires). `--inherit-config` keeps the rejected option available per run.

**Why stop+resume rather than mid-turn steering.** `codex exec` is a single non-interactive turn with no input channel once running. The TUI's Enter-injection needs a TTY that Claude cannot drive. `codex app-server` could in principle support real steering but is documented as subject to change without notice. Stop+resume was chosen with that tradeoff stated; the app-server path is recorded as unexplored, not as impossible.

**Why no instruction-injection presets.** The legacy skill wrapped methodology files in `<SystemPrompt>` tags. Dropped on the user's reasoning: Claude is the caller and can write whatever Codex needs directly into the prompt, so a preset library is a rail that accumulates unused files. Only a minimal situational-facts preamble survives (B19), because Codex asking a clarifying question in a non-interactive turn wastes the entire turn.

**Why the filter default is deferred to measurement.** `file_change` events carry paths only; the whole context risk is `command_execution.aggregated_output`, which contains full stdout including file bodies Codex has `cat`ed. Picking a default without measuring would be exactly the unjustified-number rail this project avoids, so T3 measures three workloads across four levels and the default cites its own table.

**Why no agent and no workflow.** An agent was considered and rejected: the main thread is what needs to watch the log and decide when to intervene, subagents cannot ask the user anything, and Claude's own background Bash plus Monitor already provide the parallelism. A pre-defined workflow was rejected under the same D12 logic that governs e2e — the shape of "delegate something to Codex" varies every time, so freezing it would be a flexibility tax.

**D38 — discovery rather than declaration.** Efforts are valid per model — measured on codex-cli 0.146.0, gpt-5.6-sol and gpt-5.6-terra take low/medium/high/xhigh/max/ultra, gpt-5.6-luna stops at max, gpt-5.5/gpt-5.4/gpt-5.4-mini stop at xhigh — so any static allowlist is already wrong for some model the day it is written, the same staleness D19 identified for a pinned model name. Rejected alternative: argparse `choices=`, which is exactly the list that rots.

**D39 — refuse locally rather than let the API refuse.** Before this change, an invalid model or effort was caught by the server: the run spawned, reached the API, and came back `turn.failed` with exit 1 — loud, but one wasted run late, and for a background run not discovered until the next `status`. `codex debug models` answers in ~30ms, offline, against that cost. The check is skipped entirely when the catalog cannot be read (no binary, non-zero exit, unparseable output) rather than refusing on principle: a check that blocks a run because its own lookup broke is worse than no check, so fail-open is the only safe direction, and `doctor` reports `models_catalog: null` with a warning so the gap is not silent either.

**D40 — no defaults for model, effort or timeout.** Reaffirms D19 (a hardcoded model name is a guaranteed future bug) and extends the same reasoning to `--timeout`: a default deadline would cut short exactly the long, unattended background run this skill exists to enable. The user's call, recorded rather than inferred.

**D41 — `--as-ready`: a per-thread invariant enforced per thread.** `--resume-from`'s barrier refuses the whole batch while any member of the previous group is live. The barrier was not a concurrency requirement, and the code says so: its comment gives the reason as preventing an *unintended partial start* — a per-member check would refuse only after earlier tasks had already resumed, leaving phase 2 half started against phase 1 half finished. The invariant actually being protected is one turn per thread, which is per thread, so member 3's phase 2 is safe to begin the moment member 3's phase 1 ends.

**This is deliberately the same family as D34, which was abandoned, and the difference is the whole design.** D34 dropped `--max-concurrent` because a queued run has no supervisor process, so `reap()` brands it `orphaned` within thirty seconds. `--as-ready` introduces no queue and no group supervisor: each member spawns its own supervisor immediately, exactly as before, and that supervisor waits inside `supervise()` before it spawns Codex. The run is supervised throughout, so D34's condition never arises. Anyone reaching for member-level scheduling again should start here rather than re-deriving why the obvious shape does not work.

Two things the design review caught before implementation, both worth keeping because the reasoning that produced them was wrong in a way that would repeat:

- **The first safety argument was false.** It claimed `supervisor_pid` stays alive through the wait, so `reap()` is satisfied. `supervisor_pid` is written *after* Codex spawns; during the wait it is null. The outcome held anyway — `reap()` returns early for any state outside its active tuple — but by accident, and that accident is the opposite defect: a waiter whose supervisor is killed would sit in `waiting` forever, blocking `batch clean`, further chaining, and every implicit-target command. The fix is to record `supervisor_pid` and `pgid` *before* waiting and teach `reap` about `waiting`, **in that order** — teaching `reap` first reproduces D34 exactly.
- **As designed the feature was unreachable.** Two creation-time gates refuse a phase-2 member before the wait loop is entered: the group barrier itself, and `refuse_concurrent_turn` matching the predecessor's own row. The exemption is scoped to the member's paired predecessor run id rather than granted by `--force`, because `--force` waives the check for every collision on the thread including unplanned ones, and the wait re-establishes the invariant before Codex starts rather than abandoning it.

**Why `codex_started_at` exists.** `started_at` is stamped when the run object is built, which under `--as-ready` is deliberately while the predecessor is still mid-turn. Any overlap test reading it reports a correct chained run as a violation of one-turn-per-thread — and the natural response, loosening that test, would remove the check standing between this design and the rollout corruption F4 reproduced.

Cost **113 input tokens** against a ~16 k context. Keep the preamble, and keep it non-optional for batch runs: the failure mode it prevents is fabrication, not omission. |

One incidental measurement, recorded because `orchestration.md` will cite it: the isolated per-invocation input floor on this project is **~16,016 tokens** and it is **stable under parallelism** (median identical at N=1, 2, 4 and 8). That stability is the useful claim. The absolute number is not — R8 below is the standing reminder that this figure moved 2.92× → 1.09× in two weeks, which is why `projected_cost` computes from the registry at runtime (D37) instead of baking a constant.

### Refinements forced by the sweep

Recorded here and applied to `docs/plan/codex-skill-implementation-plan.md`. None of them change a component's design — each strengthens or corrects the *rationale* the design already rests on.

- **R1 — §3.1 is per-turn setting amnesia, not merely escalation.** `resume` inherits *no* per-invocation setting from the thread; it re-derives every one from whatever config is in effect for that invocation. Measured on thread `019f995b`, one thread, three turns:

  | Turn | Invocation | `turn_context.sandbox_policy` | `reasoning_effort` |
  |---|---|---|---|
  | 1 | `exec --ignore-user-config -c sandbox_mode="workspace-write" -c model_reasoning_effort="low"` | `workspace-write` | `low` |
  | 2 | `exec resume --ignore-user-config` (no flags) | **`read-only`** — silent *downgrade* | **`None`** — dropped |
  | 3 | `exec resume --ignore-user-config -c sandbox_mode="workspace-write" -c model_reasoning_effort="high"` | `workspace-write` | `high` |

The escalation direction reproduces too, exactly as the plan recorded it: thread `019f9959` created `read-only`, resumed **with inherited config** and no sandbox flag, got `"sandbox_policy": {"type": "danger-full-access"}` with `permission_profile.file_system: {"type": "disabled"}`, and wrote `escalated_inherit.txt` containing `ESCALATED`.

Which direction you get is decided by the config layer in effect, not by the thread: inherited config on this machine escalates to `danger-full-access`; isolation downgrades to `read-only`. Isolation therefore *masks* the escalation here purely by coincidence — Codex's own built-in `exec` default happens to be `read-only`. Relying on that would be a bug: it depends on a Codex default staying put, it collapses the moment `--inherit-config` is used, and it silently breaks legitimate `workspace-write` work in the other direction. Re-injection from the registry is what makes the sandbox *stable*, and stability is the property worth stating — anti-escalation is one consequence of it.

- **R2 — `turn_context` is the verification channel, not the `<permissions instructions>` text.** Each turn appends a `{"type":"turn_context","payload":{…}}` line to the rollout carrying `sandbox_policy`, `permission_profile`, `model`, `cwd`, `workspace_roots`, and `collaboration_mode.settings.reasoning_effort`. It is structured, one line per turn, and unambiguous — strictly better than grepping a developer message. T2/I4 uses it.

- **R3 — `review` reports zero token usage.** Both V-10 runs ended `{"usage":{"input_tokens":0,"cached_input_tokens":0,"output_tokens":0,"reasoning_output_tokens":0}}` despite doing real work. `result` and `status` must not present that as a real measurement for review runs; report usage as unavailable rather than as zero.

- **R4 — the `SessionEnd` hook should match on the input's `session_id` first.** *(Superseded: the hook was removed in v0.2.0 — D23. Kept because the finding about hook input keys is still true and would matter to anyone building one.)* Plan §5.4 assumed `$CLAUDE_CODE_SESSION_ID` in the hook's environment. The hook *input* carries `session_id` directly (V-05), which is authoritative. The hook matches a recorded run if its `claude_session_id` equals **either** the input's `session_id` or the hook process's `CLAUDE_CODE_SESSION_ID` — either source alone is a single point of failure, and disagreement between them would otherwise mean killing nothing (benign) or everything (not).

- **R5 — measured resume cost curve** (isolated, same machine, `gpt-5.6-sol`), which is the concrete form of plan §3.4:

  | Invocation | Input tokens | Cached |
  |---|---|---|
  | fresh `exec`, trivial prompt | 15,871 | 13,056 |
  | fresh `exec`, trivial prompt, repo has a 2-line `AGENTS.md` | 16,410 | 0 |
  | `resume`, 1 prior turn | 31,780 | 28,160 |
  | `resume`, 2 prior turns | 47,774 | 43,264 |
  | `resume`, after an interrupted 6-command turn | 86,142 | 75,520 |

- **R6 — script path resolution comes from the skill's context header, not from any environment variable.** V-01 answered "no", which invalidates the plan §4 snippet: `${CLAUDE_PLUGIN_ROOT:-$HOME/.claude/skills/codex}` resolves to a path that does not exist under a plugin install. Three mechanisms were tested against a real install:

  | Mechanism | Works? | Evidence |
  |---|---|---|
  | `$CLAUDE_PLUGIN_ROOT` / `$CLAUDE_SKILL_DIR` in Bash | **no** | Both empty with the plugin installed and the skill active |
  | `` !`shell` `` preprocessing in a plugin SKILL.md body | **no** | The backtick expression reaches the model literally, unexpanded |
  | `Base directory for this skill: <dir>` in the skill's context | **yes** | Quoted back verbatim by a headless session from a neutral cwd |

SKILL.md now instructs the model to take the path from that context line and use it literally, double-quoted. Verified end to end: a headless session in **default** permission mode (no `--dangerously-skip-permissions`) ran `python3 "/…/.claude/skills/codex/scripts/codex_bridge.py" doctor` with **no approval prompt**, so B18 holds and the base-directory path and the `allowed-tools` pattern's expansion of `${CLAUDE_PLUGIN_ROOT}` agree.

The load-bearing consequence, written into SKILL.md with its reason: the permission pattern matches the command *text*, so a command built from a shell variable is not covered by it and would prompt on every poll — which is precisely what would make background work unusable.

- **R7 — `plugin.json` must not declare `"hooks"`.** `hooks/hooks.json` is auto-loaded for plugins; declaring it produced `Hook load failed: Duplicate hooks file detected` and the **entire plugin failed to load**, skill included. `validate_harness.py` passed clean throughout — only a real install surfaced it.

- **R8 — the isolation saving is not a stable number; the clean stream is.** The plan's §3.3 headline ("~66% of input tokens") did not reproduce. Same machine, same prompt (`Reply with exactly: OK`), no deliberate config change:

  | When | `--inherit-config` | `--ignore-user-config` | ratio | inherited `error` events |
  |---|---:|---:|---:|---:|
  | design session | 46,238 | 15,863 | 2.92× | 24 |
  | at M9, two weeks later | 17,327 | 15,837 | 1.09× | 8 |

Measured three consecutive times at M9 with identical results, so this is not noise. The isolated floor is stable to 26 tokens; what moved is how much of the user's config actually *loads* — an MCP server that fails to start contributes nothing to the prompt.

Consequences applied: SKILL.md and `environment.md` no longer quote a ratio as though it were a property, and say to measure it if it matters to a decision. **I7 was rewritten** to assert what the wrapper is actually responsible for — that `--ignore-user-config` reaches the argv and has an observable effect (0 config-error events isolated vs 8 inherited, and isolation never costing more) — instead of a token threshold, which tested the user's Codex configuration rather than this code and would fail for reasons no code change could fix.

- **R9 — the prompt must be preceded by `--`.** Found by I8 failing. `codex exec`'s `-i/--image <FILE>...` takes **multiple** values, so clap greedily consumed the following positional: the prompt became a second image path, Codex found no prompt, fell back to stdin (`/dev/null`) and exited having done nothing, with `state: failed` and no events. `exec resume`'s `-i` is single-valued, so only `exec` had it. `--` also fixes a second latent failure — a prompt beginning with `-` is rejected outright as an unknown flag (Codex's own error text suggests `--`). Now emitted unconditionally before the prompt on all three subcommands, verified against the real CLI on `exec` and `resume`.

The T1 fake `codex` had not caught this because it did not parse argv the way clap does. It now models greedy `-i` consumption and the `--` terminator and **exits non-zero when option parsing ate the prompt** — reverting the fix makes three T1 tests fail, confirming the gap is closed rather than merely patched.

### T6 — `tests/260813/`, the round's own regressions

**83 tests, ~50 s**, a second `unittest` start directory alongside `tests/legacy/`. Two directories rather than one because neither is a package: `discover -s tests` walks only as far as the first directory without an `__init__.py` and reports the empty result as `NO TESTS RAN` with exit status 0, and making them packages breaks every `from helpers import …` in the legacy suite.

Its relationship to the other tiers is a division of question, not of subject:

- **T1 (`tests/legacy/`) and T6 both answer "is this still true?"** — deterministic, cheap, repeatable. T6 holds this round's regressions and the checks the earlier tiers had no reason to write: that the suite is present at all, that the docs and the CLI still agree, and that the invariants `--as-ready` rests on hold under concurrent load.
- **The dynamic workflows answer "what have we not thought to test?"** — non-deterministic and expensive, and their findings become T6 slices. Every defect this round fixed arrived that way and left as a test here.
- **T2 and T4 remain the only tiers that touch a real Codex.** T6 reuses `tests/legacy/fake_codex/codex` rather than copying it: that shim models the real CLI's argv parsing (`-i`'s greedy consumption, the `--` terminator), and two copies drift the moment one is fixed, after which each suite verifies a different CLI and neither says which.

It carries the round's concurrency soak, whose ten oracles all read one recorded history — the driver is the expensive part, so the tenth oracle costs almost nothing more than the first. Reproducibility is stated rather than claimed: the *plan* (which worker attempts which kind of operation, in what order) is a pure function of the seed, while the targets and the OS-level interleaving are not, so a failure reports its seed and its history file and buys the same pressure rather than the same crash. The soak was checked to be able to fail — writing `meta.json` in place instead of atomically trips oracle 2, and disabling `refuse_concurrent_turn` trips oracle 5 on both seeds tried.
