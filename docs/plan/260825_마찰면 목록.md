# 마찰면 목록 — 고치지 않고 적기만 한 것 (2026-08-25)

`codex-validated-blum.md` Phase 0b의 산출물이다. 합격 기준이 *"잘 작동한다"* 만이 아니라 *"쓰는 데 헷갈림도 병목도 없다"* 이므로 대기 말고 나머지 마찰면도 봐야 하는데, 근거 없이 넓히는 것은 이 레포가 R-기록으로 남겨온 실패 방식이다. 그래서 이번 패스에서 실제로 CLI를 평범하게 쓰면서 **부딪힌 것만** 적는다. 무엇을 고칠지는 성진이 정한다.

관찰 환경: macOS 25.5.0, `codex-cli 0.147.0`, Claude Code (Opus 5, 1M), 이 레포.

## 1. `--help` 왕복 비용 — 실측했고, 생각보다 작다

| 명령 | 바이트 | 줄 |
|---|---|---|
| (최상위) | 2,130 | 40 |
| `start` | 7,812 | 119 |
| `resume` | 8,826 | 131 |
| `review` | 7,638 | 115 |
| `batch start` | 12,378 | — |
| `log` | 3,386 | 50 |
| `status` | 4,498 | 73 |
| `result` | 1,128 | 18 |

이번 패스에서 `RUN_RETURN_EPILOG`이 `start`/`resume`/`review`에 각각 ~1.1KB씩 더했다.

**판단이 필요한 지점**: 한 세션에서 `start --help`를 몇 번 읽는가. 한 번이면 ~2,000 토큰은 옵션 표면 전체값으로 싸다. 위임할 때마다 반복해서 읽는다면 최상위 `--help`에 "어느 것을 언제 읽나" 한 줄이 있어야 흡수된다 — 지금 최상위는 명령별 한 줄 요약은 주지만 *"플래그를 정하려면 여기를 읽어라"* 를 말하지 않는다. 이번 세션 관찰만으로는 반복 여부를 알 수 없다. e2e 트랜스크립트에서 세어야 답이 나온다.

## 2. 첫 호출의 경로·권한 gotcha — 이번 세션에서는 측정 불가

`bypassPermissions` 모드로 돌아서 승인 프롬프트가 애초에 뜨지 않았다. 절대 경로 + 한 줄 제약을 어겼을 때의 실제 비용은 이 세션이 증거를 못 만든다. 기계로 잡을 여지는 있다 — `PreToolUse` 훅이 `codex_bridge.py`를 부르는 Bash 명령에서 `$` 로 시작하는 경로나 줄바꿈 continuation을 보면 거절하고 이유를 돌려주는 것. 다만 **훅은 이 레포에 아직 한 개도 없다**(`.claude/settings.local.json`만 있음). 첫 훅을 들이는 비용이 이 gotcha의 비용보다 큰지가 실제 질문이다.

## 3. `thread_id: null` — Phase 1의 epilog 이전으로 충분해 보인다

이번 패스에서 `RUN_RETURN_EPILOG`으로 옮겼다. 반환 JSON 자체가 말해야 하느냐는 질문에 대해: `null` 옆에 설명 필드를 붙이면 정상 경로마다 노이즈를 내는 필드가 하나 생긴다(`unparsed_events`가 0일 때 생략되는 것과 같은 이유). **epilog으로 두고 관찰**을 권한다. 이번 세션에서는 null이 한 번도 나오지 않아 호출자가 실패로 읽는 장면 자체를 못 봤다.

## 4. 새로 발견 — 무장한 대기 뒤에 `result --run`은 대개 여벌이다

P1 프로브에서 실제로 겪은 것이다. 백그라운드 팔로워가 끝나고 알림이 왔을 때, 출력 파일에는 이미 이게 들어 있었다:

```
thread 01a036f1-…
turn.started
msg PONG
turn.completed in=18338 cached=5888 out=6 reasoning=0
run.completed run=… exit=0
```

`msg`는 **어느 레벨에서도 잘리지 않는다**(`_events.py`의 설계). 즉 무장된 대기를 하고 나면 에이전트의 최종 메시지는 이미 손에 있고, `result --run`은 한 번 더 왕복해서 같은 문장을 가져온다. `result`가 더 주는 것은 `usage`·`json`(스키마 런)·구조화된 필드다.

SKILL.md의 흐름 예시는 여전히 마지막 줄에 `result --run`을 둔다. 그게 맞는 경우(스키마 런, 사용량이 필요한 경우, 배치)와 여벌인 경우(무장 대기 후 단일 런)를 구분해 줄지가 판단 지점이다. **이번 패스에서는 건드리지 않았다** — 근거가 프로브 한 번이라 얇다.

## 5. 작은 것들 (기록만)

- `log --follow`의 `--since` 기본값은 0이라, **이미 진행 중인** 런에 무장을 걸면 지금까지의 로그 전체를 출력 파일에 재생한다. 컨텍스트로 들어오지 않으므로 실해는 없지만, 알림 뒤에 그 파일을 `Read` 할 때 처음 읽는 사람은 놀란다. V-23에 기록.
- `--since`가 EOF를 넘으면 조용한 0바이트가 아니라 이유가 붙은 거절로 끝난다. 이건 마찰이 아니라 잘 된 것 — 기록해 둔다.
- 계획서 Phase 6이 적은 `python3 -m unittest discover -s tests -p 'test_*.py'`는 **이 레포가 R30으로 문서화해 둔 깨진 형태다** (`NO TESTS RAN`, 종료 코드 0). 네 디렉터리를 각각 돌려야 한다. 계획서 쪽의 오류이고 CONTRIBUTING.md가 맞다.
